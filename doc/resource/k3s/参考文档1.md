# linux下，有一个链接文件kubectl，链接的是k3s文件，但为什么我执行kubectl命令和执行k3s命令结果不一样呢
```text

在Linux环境下，即使kubectl是k3s的软链接，执行结果仍可能不同，主要原因如下：

一、权限与配置文件差异

默认配置文件权限限制‌
k3s默认生成的配置文件/etc/rancher/k3s/k3s.yaml仅允许‌root用户‌访问。若直接以非root用户运行kubectl，会因权限不足导致命令失败。
解决方案‌：

bash
Copy Code
mkdir -p $HOME/.kube
sudo cp /etc/rancher/k3s/k3s.yaml $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config
export KUBECONFIG=$HOME/.kube/config  # 临时生效


或将其写入.bashrc文件永久生效。

配置文件路径未正确指向‌
kubectl默认会读取$HOME/.kube/config，而k3s可能直接调用/etc/rancher/k3s/k3s.yaml。若未正确配置KUBECONFIG环境变量，可能导致两者访问不同集群配置。

二、命令行为差异

k3s封装特性‌
k3s是轻量级Kubernetes发行版，其kubectl功能通过封装实现。直接执行k3s kubectl可能隐含附加参数（如--kubeconfig），而软链接的kubectl未包含这些参数，导致行为差异。

版本兼容性问题‌
k3s内置的Kubernetes版本可能与独立安装的kubectl版本不一致。例如，k3s v1.33.1可能使用定制组件，导致命令输出格式或功能与标准kubectl不同。
验证方法‌：

bash
Copy Code
kubectl version --client  # 查看kubectl版本
k3s --version             # 查看k3s版本

三、环境变量与路径冲突
多版本共存问题‌
若系统中同时存在通过其他方式（如手动下载或包管理器）安装的kubectl，环境变量PATH可能优先调用其他版本，而非软链接的k3s。
检查路径优先级‌：
bash
Copy Code
which kubectl  # 确认实际执行路径

排查建议
统一配置与权限‌
按上述步骤配置$HOME/.kube/config并验证权限，确保kubectl和k3s使用相同的配置文件。
执行完整命令对比‌
分别运行以下命令观察差异：
bash
Copy Code
kubectl get nodes --kubeconfig=/etc/rancher/k3s/k3s.yaml
k3s kubectl get nodes

检查组件健康状态‌
使用k3s check-config验证集群组件是否正常运行，排除因网络策略或组件故障导致的行为不一致。

```

# k3s服务器节点宕机后，代理节点还能用吗
```text
k3s集群中服务器节点（Server）宕机后，代理节点（Agent）的可用性取决于集群架构设计：

单节点Server架构‌

若集群仅有‌单个Server节点‌且未配置高可用，该节点宕机后：
代理节点上的‌现有Pod会继续运行‌，但无法接收新的调度指令或更新配置
控制平面功能完全失效‌（如API Server不可用），无法创建/删除Pod或执行其他集群管理操作

高可用集群架构‌
当部署了‌多Server节点+外部数据库‌（如ETCD/MySQL/PostgreSQL）时：

至少需要‌2个存活Server节点‌以维持控制平面运行（3节点集群允许1节点故障）
代理节点可‌持续接收调度指令‌，Pod故障转移与新服务部署不受影响
需通过kube-vip等工具实现虚拟IP漂移，保障API Server访问连续性

关键影响因素‌：

控制平面组件（API Server、Scheduler）的存活状态决定代理节点的可管理性
使用外部数据库是保障状态持久化和故障恢复的基础条件
宕机节点恢复后需重新加入集群或通过脚本更新节点信息

注：测试环境下直接关机可能导致Pod状态异常（如卡在Unknown状态），建议通过kubectl drain主动驱逐Pod触发调度
```

# k3s节点宕机后，再重启恢复会自动加入集群嘛
```text
k3s节点宕机后能否自动重新加入集群取决于节点类型和配置方式，具体可分为两种情况：

一、控制平面节点（Server节点）

单Server架构‌

若集群仅有‌1个Server节点‌，宕机后即使硬件恢复：
无法自动重新加入‌原集群，必须通过k3s-uninstall.sh脚本清理配置后手动重建集群
数据存储若采用嵌入式SQLite，宕机恢复可能导致数据不一致，需重新初始化

高可用架构‌

当集群配置了‌多Server节点+外部数据库‌（如MySQL/PostgreSQL）：
宕机节点重启后‌自动重新加入集群‌（需满足：/etc/rancher/k3s/config.yaml中的token和server-url未被修改)
若节点证书过期或存储损坏，需手动执行k3s server --cluster-reset恢复
二、工作节点（Agent节点）

常规配置‌

Agent节点重启后‌自动重新注册‌到集群（前提条件）：
安装时通过K3S_URL和K3S_TOKEN参数指定了Server节点地址及认证令牌
/etc/systemd/system/k3s-agent.service中的服务配置未被篡改

异常处理‌

若节点因证书失效无法连接API Server，需：
① 在Server节点生成新token：cat /var/lib/rancher/k3s/server/node-token
② 在Agent节点更新K3S_TOKEN并重启服务
当节点信息残留时，需在Server端执行kubectl delete node <node-name>清理旧记录
对比总结
节点类型	自动加入条件	需人工干预场景
Server节点	多Server架构且配置未损坏	单节点/证书失效/数据库故障
Agent节点	服务配置及token有效	网络配置变更/token过期

注：生产环境建议通过systemctl enable k3s-server或k3s-agent设置服务自启动，并定期备份/etc/rancher/k3s/目录下的配置文件。
```

# k3s代理节点能apply pod嘛
```text
k3s代理节点（Agent节点）默认情况下无法直接使用kubectl apply创建Pod‌，原因如下：

权限与控制平面分离‌

Agent节点设计为‌工作节点‌，仅负责运行Pod而非管理集群状态
kubectl apply命令需访问‌API Server‌（位于Server节点），而Agent节点未默认配置访问权限

RBAC限制‌

k3s默认角色绑定（RoleBinding）未赋予Agent节点执行create或update等操作的权限
若无显式授权，Agent节点无法通过kubectl提交资源定义到API Server

若需在Agent节点执行kubectl apply，需额外配置：‌

kubeconfig文件分发‌
从Server节点复制/etc/rancher/k3s/k3s.yaml到Agent节点
修改配置中的server地址指向API Server（如https://<server-ip>:6443)
权限提升‌
在Server节点创建ServiceAccount并绑定ClusterRole（如edit或admin)
通过kubectl config set-credentials将ServiceAccount token注入Agent节点的kubeconfig

注：生产环境不推荐此操作，以避免安全隐患。常规做法应‌仅在Server节点或运维终端执行集群管理操作‌。
```

# k3s集群node宕机其上的pod不会立即转移的问题
```text
K3s集群中node节点宕机后其上的pod不会立即转移
官方解释

1、说明
​ 搭建完成k3s集群后，为了测试k3s集群的性能。选择直接将node关机，查看对应的pod有没有转移。

经过一通操作之后发现 rancher集群上显示关闭的node对应的pod转态变为Unknow，但是没有新建出pod。这是怎么回事儿呢？

2、原因
一通google之后，找到了参考链接中的说法。

在 Kubernetes v1.13 版本中，TaintBasedEvictions特性是默认开启的。请查阅 Kubernetes: Taint based Evictions 获取更多信息。

kube-apiserver (Kubernetes v1.13 版本及以后)

default-not-ready-toleration-seconds: 表示 notReady:NoExecute 容忍的容忍时间。notReady:NoExecute 被默认添加到没有该容忍的所有 Pod。

default-unreachable-toleration-seconds: 表示 unreachable:NoExecute 容忍的容忍时间。unreachable:NoExecute 被默认添加到没有该容忍的所有 Pod。

原来是自kubernetes v1.13版本后默认设置了pod转移时间。

3、更改默认pod的转移时间
k3s官方提供了实例文件

apiVersion: apps/v1
kind: Deployment
metadata:
  name: busybox-deployment
  labels:
    app: busybox
spec:
  replicas: 3
  selector:
    matchLabels:
      app: busybox
  template:
    metadata:
      labels:
        app: busybox
    spec:
    ########################
      tolerations:
      - effect: NoExecute
        key: node.kubernetes.io/unreachable
        operator: Exists
        tolerationSeconds: 2
      - effect: NoExecute
```

# k3s‌证书域名不匹配，怎么解决
```text
在k3s环境中解决证书域名不匹配问题时，需重点关注证书的SAN（Subject Alternative Name）字段配置和k3s的服务参数调整。以下是具体解决方案：

1. ‌验证现有证书的域名信息‌

检查当前k3s服务端证书的SAN字段是否包含目标访问域名或IP：

bash
Copy Code
openssl x509 -in /var/lib/rancher/k3s/server/tls/server.crt -text -noout | grep -A1 "Subject Alternative Name"


若输出未包含所需域名或IP，需重新生成证书。

2. ‌重新生成k3s证书‌

通过调整k3s服务启动参数，强制生成包含正确SAN的证书：

修改k3s服务配置‌：
bash
Copy Code
vi /etc/systemd/system/k3s.service

在ExecStart行追加--tls-san参数指定域名或IP（可叠加多个）：
text
Copy Code
--tls-san your.domain.com --tls-san 10.0.0.1

重启服务并生效‌：
bash
Copy Code
systemctl daemon-reload
systemctl restart k3s


此操作会生成新证书，SAN字段将包含指定域名/IP。

3. ‌更新kubeconfig文件‌

证书更新后，需同步客户端配置：

bash
Copy Code
cp /etc/rancher/k3s/k3s.yaml ~/.kube/config
sed -i "s/127.0.0.1/your.domain.com/g" ~/.kube/config


确保kubectl指向正确的API服务器地址。

4. ‌检查Traefik Ingress证书配置‌

若通过Ingress暴露服务，需验证Traefik是否正确引用证书：

查看证书Secret‌：
bash
Copy Code
kubectl get secret -n kube-system | grep traefik-default-cert

绑定域名到证书‌：
在Ingress资源中指定tls字段：
yaml
Copy Code
tls:
- hosts:
  - your.domain.com
  secretName: traefik-default-cert  # 或自定义证书Secret

确保Secret中的证书包含匹配域名。
5. ‌多域名场景处理‌

若需支持多个域名或通配符：

生成通配符证书‌：在k3s启动参数中添加--tls-san *.example.com。
手动部署多域名证书‌：替换/var/lib/rancher/k3s/server/tls/server.crt和server.key文件，并重启服务。
6. ‌排除时间同步问题‌

虽然域名错误是主因，仍需确认系统时间无误：

bash
Copy Code
timedatectl status  # 检查时间同步状态
ntpdate pool.ntp.org  # 手动同步时间（若偏差）


避免因时间误差导致的附加验证失败。

注意事项‌：

避免使用--insecure-skip-tls-verify跳过验证（仅限测试环境）。
生产环境建议使用Let's Encrypt或TrustAsia等可信CA签发的证书，减少兼容性问题。
```

```text
1.3.2 清理节点
在使用 Containerd 作为容器运行时环境CRI，则可以使用k3s-uninstall.sh直接删除K3s集群环境
在使用 Docker 作为容器运行时环境CRI，则即使使用k3s-uninstall.sh直接删除K3s集群环境，也会残留部分 K3s 容器信息，需要管理员手动删除 K3s 集群的容器，docker rm -f $(docker ps -aq)，同时建议推荐使用Rancher - K3s的清理脚本运行
以下操作将删除节点中的数据（包括容器，卷，iptables 等），在执行命令之前，请先查看该脚本，确保您理解这个脚本在做什么，并且确保已进行了数据备份。

Reference：https://docs.rancher.cn/docs/rancher2/trending-topics/cleaning-cluster-nodes/_index/#%E6%B8%85%E7%90%86%E8%84%9A%E6%9C%AC

#!/bin/bash

KUBE_SVC='
kubelet
kube-scheduler
kube-proxy
kube-controller-manager
kube-apiserver
'

for kube_svc in ${KUBE_SVC};
do
  # 停止服务
  if [[ `systemctl is-active ${kube_svc}` == 'active' ]]; then
    systemctl stop ${kube_svc}
  fi
  # 禁止服务开机启动
  if [[ `systemctl is-enabled ${kube_svc}` == 'enabled' ]]; then
    systemctl disable ${kube_svc}
  fi
done

# 停止所有容器
docker stop $(docker ps -aq)

# 删除所有容器
docker rm -f $(docker ps -qa)

# 删除所有容器卷
docker volume rm $(docker volume ls -q)

# 卸载mount目录
for mount in $(mount | grep tmpfs | grep '/var/lib/kubelet' | awk '{ print $3 }') /var/lib/kubelet /var/lib/rancher;
do
  umount $mount;
done

# 备份目录
mv /etc/kubernetes /etc/kubernetes-bak-$(date +"%Y%m%d%H%M")
mv /var/lib/etcd /var/lib/etcd-bak-$(date +"%Y%m%d%H%M")
mv /var/lib/rancher /var/lib/rancher-bak-$(date +"%Y%m%d%H%M")
mv /opt/rke /opt/rke-bak-$(date +"%Y%m%d%H%M")

# 删除残留路径
rm -rf /etc/ceph \
    /etc/cni \
    /opt/cni \
    /run/secrets/kubernetes.io \
    /run/calico \
    /run/flannel \
    /var/lib/calico \
    /var/lib/cni \
    /var/lib/kubelet \
    /var/log/containers \
    /var/log/kube-audit \
    /var/log/pods \
    /var/run/calico \
    /usr/libexec/kubernetes

# 清理网络接口
no_del_net_inter='
lo
docker0
eth
ens
bond
'

network_interface=`ls /sys/class/net`

for net_inter in $network_interface;
do
  if ! echo "${no_del_net_inter}" | grep -qE ${net_inter:0:3}; then
    ip link delete $net_inter
  fi
done

# 清理残留进程
port_list='
80
443
6443
2376
2379
2380
8472
9099
10250
10254
'

for port in $port_list;
do
  pid=`netstat -atlnup | grep $port | awk '{print $7}' | awk -F '/' '{print $1}' | grep -v - | sort -rnk2 | uniq`
  if [[ -n $pid ]]; then
    kill -9 $pid
  fi
done

kube_pid=`ps -ef | grep -v grep | grep kube | awk '{print $2}'`

if [[ -n $kube_pid ]]; then
  kill -9 $kube_pid
fi

# 清理Iptables表
## 注意：如果节点Iptables有特殊配置，以下命令请谨慎操作
sudo iptables --flush
sudo iptables --flush --table nat
sudo iptables --flush --table filter
sudo iptables --table nat --delete-chain
sudo iptables --table filter --delete-chain
systemctl restart docker

1.5 节点标签和污点

curl -sfL https://get.k3s.io | sh -s - --node-label app=k3s --node-taint special=true:NoSchedule
```

```text
在 CentOS 8 中执行 yum install ntpdate -y 命令时，可能会遇到报错信息，提示未找到匹配的参数。这是因为在 CentOS 8 中，ntpdate 已经被弃用，取而代之的是 chrony。

示例

yum install ntpdate -y
错误：没有任何匹配: ntpdate
解决方法

1. 安装 Chrony

在 CentOS 8 中，使用 chrony 来替代 ntpdate 进行时间同步。

步骤:

sudo yum install -y chrony
2. 配置 Chrony

安装完成后，需要配置 chrony 来同步时间服务器。

步骤:

sudo vim /etc/chrony.conf
注释掉原有的时间服务器地址，并添加新的时间服务器地址，例如阿里云的时间服务器：

server ntp1.aliyun.com iburst
3. 启动并启用 Chrony 服务

配置完成后，启动并设置 chronyd 服务开机自启。

步骤:

sudo systemctl restart chronyd.service
sudo systemctl enable chronyd.service
4. 验证时间同步

最后，可以使用 date 命令来验证时间是否同步成功。

步骤:

date
通过以上步骤，可以成功解决 yum install ntpdate -y 报错的问题，并使用 chrony 实现时间同步。
```

# K3S的一些基础使用配置
```text
关于 K3S
K3S 是专门针对 IoT 和边缘计算(Edge computing)设备开发的轻量级 Kubernetes 集群软件，特别适合低配置硬件的设备上使用比如树莓派(Raspberry Pi)或者OpenWrt的路由器设备上。K3S有单机和高可用(High-Availability)两种使用方式，官方文档在这里。

安装 K3S
K3S 的安装非常简单，你可以通过一下命令直接安装。

curl -sfL https://get.k3s.io | sh -
但是有几个点需要注意的是，如果你的公网IP没有直接绑定到机器上（通过命令 ifconfig 查看）那么则需要加上--tls-san ip这个参数，以到达从公网通过 kube-config 来访问集群。

curl -sLS https://get.k3s.io | INSTALL_K3S_EXEC='server --tls-san 10.10.10.10' sh -
等待安装成功后，就可将 kubernetes 集群的 kubeconfig 文件下载本地电脑中，默认存放到 ~/.kube/ 目录中

cat /etc/rancher/k3s/k3s.yaml
修改 kubeconfig 文件的IP地址内容来达到远程访问管理集群的目的。

server: https://10.10.10.10:6443
接着在本地电脑的 Terminal 命令行工具中导出 kubeconfig 的环境变量即可。

export KUBECONFIG=~/.kube/my-k3s
添加 Worker 节点
如果有多台机器组成集群的话，可以给安装命令添加 K3S_TOKEN=mynodetoken 来完成。
K3S_TOKEN 存储在 master 节点的 /var/lib/rancher/k3s/server/node-token

如果 Worker 节点已经安装成功，则可以通过下面的命令来加入集群。

K3S_TOKEN=SECRET k3s agent --server https://fixed-registration-address:6443
Helm
Helm 是 kubernetes 非常好用的软件管理工具，K3S 默认开启 Helm 的支持。本地电脑可以通过官方文档的页面进行安装。安装后需要手动添加 Stable Repo

helm repo add stable https://kubernetes-charts.storage.googleapis.com
注意：本文例子都使用 Helm3 来操作，Helm 的 2.x 版本与 3.x 版本使用上有些不同。
Traefik
Traefik 是 kubernetes 的路由组件，可以将访问流量分发到不同的服务，可以简单理解为 Nginx。K3S 同样默认安装了该组件，你可以试着访问你的 IP 地址看看，如果你能看到一个 404 网页，那么说明 traefik 组件已经正常工作了。

Local Storage Provider
K3S 同样默认安装了本地存储服务，方便支持部署有状态的服务，比如 MySQL。你可以通过下面的命令查看状态。

kubectl get storageclass

## 你将会看到如下的信息
NAME                   PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
local-path (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false                  47m
TLS 证书的自动化配置
Let’s Encrypt 是一个免费的 TLS 证书颁发服务，我们可以利用它来为我们自己的服务做 HTTPS 加持。因为 Let's Encrypt 颁发的证书只有 90 天的有效期，所以我们需要一个定时任务在证书过期之前延续有效期。还有就是当我们部署新服务的时候，也需要自动帮我们生成一个新的证书。

cert-manager 就是这样的一个服务，根据官方文档的描述，我们可以通过下面的方式来安装它。

# 首先我们添加自定义资源
kubectl apply --validate=false -f https://raw.githubusercontent.com/jetstack/cert-manager/v0.13.0/deploy/manifests/00-crds.yaml

# 接着创建命名空间
kubectl create namespace cert-manager

# 添加 Helm 的 Repo
helm repo add jetstack https://charts.jetstack.io

# 最后通过 Helm 进行安装
helm install \
  cert-manager jetstack/cert-manager \
  --namespace cert-manager \
  --version v0.13.1
接下来需要创建一个 Issuer 资源，用来关联 Let's Encrypt 操作证书，关于 cert-managger 的 Issues 概念的更多信息，可以查看官网文档

# 下面这条命令，会在当前目录创建一个 letsencrypt-prod-issuer.yaml 文件，然后写入下面。
cat <<EOF > letsencrypt-prod-issuer.yaml
apiVersion: cert-manager.io/v1alpha2
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    # You must replace this email address with your own.
    # Let's Encrypt will use this to contact you about expiring
    # certificates, and issues related to your account.
    email: gongzili456@gmail.com
    server: https://acme-v02.api.letsencrypt.org/directory
    privateKeySecretRef:
      # Secret resource used to store the account's private key.
      name: letsencrypt-prod
    # Add a single challenge solver, HTTP01 using nginx
    solvers:
      - http01:
          ingress:
            class: traefik
EOF

# 然后通过上面创建的文件来创建 Issues 资源
kubectl apply -f letsencrypt-prod-issuer.yaml
安装应用
现在我们已经拥有一个完备的 kubernetes 集群了，是时候安装一个应用了。这里选用安装 nginx 项目来达到演示效果，你可以在这里查看部署的配置文件。

kubectl apply -f https://gist.githubusercontent.com/gongzili456/6f03623771ed02ea4a937aa969ac6d2d/raw/e156ebf8a4d168b7a8562a3a827daf8f22a6a1d8/nginx-k8s.yaml
删除演示应用

kubectl delete -f https://gist.githubusercontent.com/gongzili456/6f03623771ed02ea4a937aa969ac6d2d/raw/e156ebf8a4d168b7a8562a3a827daf8f22a6a1d8/nginx-k8s.yaml
至此我们拥有了一个基本可用的部署环境，方便我们做 side project。

https://sspai.com/post/59081
```

```text


/var/lib/rancher/k3s/agent/serving-kubelet.crt: Node password reje
在 Kubernetes 集群中，如果你遇到了关于 /var/lib/rancher/k3s/agent/serving-kubelet.crt 文件的错误，特别是涉及到“Node password rejected”的问题，这通常是因为 kubelet 服务在启动时无法正确验证其证书。这种情况可能由多种原因引起，以下是一些解决步骤和检查点：

1. 检查证书的有效性和完整性
确保 serving-kubelet.crt 和相应的 serving-kubelet.key 文件没有损坏，并且证书是有效的。你可以使用 openssl 命令来检查证书的有效性：

openssl x509 -in /var/lib/rancher/k3s/agent/serving-kubelet.crt -text -noout
2. 确认证书的颁发者
确保证书是由 Kubernetes 集群信任的 CA（证书颁发机构）签发的。如果不是，你需要替换为正确的 CA 签发的证书。

3. 重新生成证书
如果证书存在问题或过期，你可以尝试重新生成 kubelet 的证书。对于使用 k3s 的环境，你可以通过以下命令重新生成证书：

sudo k3s crictl stopp  # 停止 k3s 服务
sudo rm -f /var/lib/rancher/k3s/agent/serving-kubelet.crt /var/lib/rancher/k3s/agent/serving-kubelet.key  # 删除旧的证书和密钥文件
sudo systemctl restart k3s  # 重启 k3s 服务
4. 检查 kubelet 配置
确保 kubelet 的配置文件（通常是 /etc/rancher/k3s/k3s.yaml 或 /etc/kubernetes/manifests/kubelet-config.yaml）中的证书路径设置正确。例如：

server: https://your-server-address:6443
image-service-endpoint: your-image-service-endpoint
tls-cert-file: /var/lib/rancher/k3s/agent/serving-kubelet.crt
tls-private-key-file: /var/lib/rancher/k3s/agent/serving-kubelet.key
5. 查看日志获取更多信息
查看 kubelet 和 k3s 的日志可能会提供更多关于为什么证书被拒绝的线索：

journalctl -u k3s
journalctl -u kubelet
6. 确认节点身份和权限
确保 kubelet 的用户和权限设置正确，特别是当涉及到文件访问和执行权限时。

通过上述步骤，你应该能够诊断并解决“Node password rejected”的问题。如果问题仍然存在，可能需要更详细地检查集群的网络配置或与你的 Kubernetes 发行版（如 k3s）的特定问题相关的问题。在某些情况下，重新部署或恢复 k3s 节点也可能是一个解决方案。
```
